# Pult idle token cost

Owner's words (to Pult): «Пропналізуй доцільність пульта... Чи не спалює це постійно токени», «Напиши керівнику плагіна». To P, on the stopgap «start the Pult conversation fresh once a day»: «Це вирішення симптому. Обговорення давай» (2026-11-20).

## Pult's finding (not measured in tokens)
- An idle Pult session costs nothing; the cost is the phone-push design. `plugins/pult/scripts/watch-log.py` exits with «time limit» about every 2 h, and each exit wakes the Pult model turn.
- Each wake re-reads the whole hub conversation, which resumes for days (transcript about 1.5 MB); at a 2 h gap the prompt cache (about 1 h) is cold, so each no-news wake pays the full context. About 12 wakes a day, almost all with nothing to push. The host also forces visible output after «no text» exits.
- Pult's options: (1) `watch-servers.ps1` pushes GIVEUP / GIVEUP-TASK / RESTART-LEAD-FAILED to the phone itself through a non-Claude channel, so Pult needs no log watcher; (2) start the hub conversation fresh regularly (stopgap, rejected by the owner as a symptom fix); (3) drop phone push.

## Checked by P
- The 2 h is self-imposed: `watch-log.py:104` `--max-minutes` default 120. Pult claims the host caps background Bash tasks at 2 h: not checked.
- The project leads have the same shape (their session watcher exits every 2 h for a skill update check), but only while they have active sessions.

## Measured (2026-11-20, from the transcripts, tokens only)
- Pult hub (Opus), 2026-11-19..20: about 13 wakes a day, gap about 110 min; 22 of 22 wakes pushed nothing; 21 of 22 cold (each rewrites about 110k tokens to the cache and reads about 230k). About 4.4M tokens a day for nothing.
- The 2 h is the host's cap on a background Bash run (a 125-min run was killed at 120 min); the hub then re-armed itself with `--max-minutes 110`, written nowhere in the plugin. The Monitor tool caps at 30 min, so no in-session watcher avoids the wakes.
- Leads cost more: Zhratva lead about 18M tokens a day on 11-19 and 11-20 (contexts 340k-540k, cold wakes every 2 h), 1 push in 33 wakes; Prishch lead 7 idle wakes on 11-19.
- No way found for a script to wake a running session (`claude` CLI has no send; `restart-leads.ps1 -Ask` writes a file the lead's own watcher reads). Paid spend of this task: about 0.013 USD (two Haiku push tests).
- Total of idle wakes 2026-11-15..20 (retro units, Opus 1.5): 23.6M units, about 3.4% of a weekly limit; Pult hub 87% of its own usage, Zhratva lead 20%, Prishch lead 11%; about 85% of it is cache writes.

## Goal
Find with the owner the cause-level fix: what must wake a model at all, and what the owner gets on the phone. Measure before deciding where cheap (tokens per wake, wakes per day). Write the agreed design in «Owner's approval» here.

## Draft design (agreed point by point 2026-11-20; the change list is not approved yet)

Cause: a Claude session is woken only to re-arm a watcher the host kills every 2 h. Fix: no model keeps a watcher; the server watcher (`plugins/pult/scripts/watch-servers.ps1`, already a non-Claude process) does all watching and wakes a model only on a real event. One running script; plus a prompt hook.

1. Pult keeps no watcher. `watch-log.py` is no longer armed by Pult; `rules/hub.md` "Phone push" is rewritten (no re-arm, no forced-output text for time-limit exits).
2. Pult events (GIVEUP, GIVEUP-TASK, RESTART-LEAD-FAILED, as today): `watch-servers.ps1` restarts the Pult session (stop, then resume the same conversation, as `restart-leads.ps1` does for leads) with a message holding the event line(s). Pult then sends the PushNotification as today and writes the cause and proposed fix in its chat.
3. Silence before a restart: Pult must be idle (`claude agents --json` status) and its transcript .jsonl unchanged for 5 minutes (owner chose 5, not 10). Otherwise the script re-checks each round; events are queued, never dropped.
4. Pult down or failing to start: the script sends the push itself through a one-shot session: `claude -p --no-session-persistence --model haiku --allowedTools PushNotification` (checked: runs hidden from a script, about 0.006 USD). Text says what to do, e.g. «Pult не піднявся - запусти його на комп'ютері» plus the event. Why no persistence: the owner dislikes extra sessions in lists; a tap on that push likely leads nowhere (not checked), so the text must be self-sufficient.
5. While the owner talks to Pult: a UserPromptSubmit hook of the pult plugin, only in the hub session (cwd is exactly home, as `hooks/hub-rules.py` detects), adds the new problem lines (since the last delivered one; keep a position file) as additionalContext; silent when there is nothing new, so no model step and no tokens. Pattern: `plugins/dev-kit/hooks/owner-session-note.py`.
6. Leads, same scheme (owner: «так»): a lead keeps no `dev-kit-sessions watch` of its own. `watch-servers.ps1` runs the same session check (reuse `cmd_watch` logic in `plugins/dev-kit/scripts/sessions.py` as a one-shot round, not a copy) for each lead with registered C sessions; on an event line (gone, finished, limited, stale, restart requested) it restarts that lead with the line(s) under the rule of point 3. The same prompt hook for a lead's owner messages (the dev-kit plugin, lead sessions only). The plugin-update reason of the 2 h exit is already covered by `watch-servers.ps1` and `restart-leads.ps1 -Ask`; the restart request (exit 7) must reach the lead the same way. Update `project-lead/SKILL.md` (the watcher arming and "at least every 2 hours" lines, 609 and 734) and `hub.md:143`.
7. Not checked, builders check first: how to resume a background session with a first message from a script; whether a push from a restarted Pult reaches the phone when the owner is away (two tests with the owner at the PC were skipped by Claude as «terminal is active»; this needs the owner away from the PC for about 10 minutes).
8. Success check after the build: from the transcripts, Pult and a lead with no events show no wakes for a day; one forced GIVEUP gives one push and the fix line in Pult.
9. Critical problems in Pult's reports (owner, 2026-11-20, «так» to each point): Pult's status shows a short list of critical problems, technical and token ones. A token problem is critical only when a session spent over 2% of the weekly limit in a day, or wasted over 0.5% in a day (waste: idle wakes, cold restarts, bloated context, as in the BACKLOG entry «Retro: token waste findings»). The thresholds are first checked on the scans of the last 5 days: how many lines they would have given. Each problem is shown once and again only when it grew. The numbers come from the daily retro scan (`retro.py`, a script, no model), so the delay is at most a day.
10. Problems that can wait (below those thresholds) go to the retro as priority items: first in the reviewer's list of the retro session (owner: «Всі проблеми які можуть почекать, потрібно виносить на ретро приорітетними»).
11. Phone push for tokens only when a session's conversation grows past 700k tokens (input + cache read + cache write of its last call; checked readable: the Zhratva lead reached 703k), once per session; the push says to move it to a new session. Checked by `watch-servers.ps1` on the last call of each live session, not by the daily scan (owner: «пуш є сенс коли сесія виросла більш ніж 700к токенів... мені треба перенести її»). Other token problems wait for the status.
12. Critical technical problems stay as today: GIVEUP, GIVEUP-TASK, RESTART-LEAD-FAILED; the rest the server watcher heals itself.
13. A lead's own conversation size (owner, 2026-11-20, «так»; the owner said leads often miss this moment). Cause checked: `project-lead/SKILL.md` checks only its C sessions' fill (limit 0.5, "Refresh an overfull C", lines 658-678); for P itself only "Restart P" (line 721) exists, with no trigger, and it needs the owner's `/clear`. Agreed:
    - P checks its own fill too (same limit 0.5, half the context window) and at the nearest safe point saves a handoff (`continue-work-in-another-context save`).
    - `watch-servers.ps1` starts the fresh lead session from that handoff by itself when the lead is idle (same name, model, effort, mode; first prompt `/continue-work-in-another-context load <file>`), then stops the old one; no owner action. A lead's state already lives in project files and the registry.
    - The 700k push (point 11) stays as the backstop when the move did not happen.

## Design review (sonnet reviewer, 2026-11-20), open until the owner decides
- Pult is a `claude remote-control --continue` server (start-servers.ps1:137-140), not a background session: no first prompt, no Pult-only stop. Restarting Pult with a message (points 2-4) has no mechanism. Proposed: the script always pushes the events through the one-shot session; Pult learns them from the hook (point 5) or «статус».
- An event restart of a lead reuses the heavy plugin-update first prompt (SKILL.md:749-760; wakes every C, full status). Needs a light first prompt that reads an events file; event text must not be passed as a command argument (resume-lib.ps1:21-22).
- Cost unmeasured: an event restart is a cold re-read of the lead's context, the same price as an idle wake. Count the non-time-limit watcher exits (gone, finished, limited, stale) per lead over the last 5 days first; batch several events into one restart; decide in the script which stale lines need a model.
- A one-shot round of cmd_watch does not exist: LIMITS/STALE marks are written at detection (sessions.py:692-709, 764-783), the `gone` grace is in memory (sessions.py:817-830, 934). Split detection from marking; keep the queue in a file; mark only after delivery.
- Point 13 handoff: fights hub.md:149 («always resume the same conversation»); the first prompt must load the project-lead skill; stop the old session before starting the new one (two sessions with one name split C reports); unsure whether the owner's phone chat follows a fresh session.
- Messages sent to a lead while it is stopped are lost (SKILL.md:761-766): re-check idle right before the stop.
- The lead hook needs a per-session events file (`events-<sessionId>.json`) shared with the restart path, so lines are not shown twice.
- Wider rewrite scope: SKILL.md:66-72, 246-256, 398, 582-649, 726, 744-754; hub.md:112-148, 164 (status is read-only, but «shown once» needs state); docs/tech/map.md; pult README; watch-log.py and its tests.
- Thresholds: the weekly limit estimate is about 30% uncertain; 0.5%/day waste may never fire (hub idle about 0.45%/day); express 700k as 0.7 of the window.
- Latency of a `gone` event grows from 1-2 min to about 11 min; the stale reminder text («кеш згорить за ~40 хв») would be false.
- Migration: ship dev-kit and pult together; `restart-leads.ps1 -Ask` request path is dead without a lead watcher.
- Unverified: does a lead with no watcher show idle; lead cache TTL 5 min or 1 h; one-shot push reaching the phone with the owner away.

## Wake by message, checked live (2026-11-20)
- A one-shot `claude -p --model haiku --permission-mode auto --no-session-persistence --allowedTools SendMessage,ListAgents` session lists the live sessions (Pult shows as `interactive · idle`, leads as `bg`) and its SendMessage to «Pult» was taken without the owner's approval: Pult answered «тест отримано» in its chat within seconds (Pult transcript, 19:56:51Z). No stop, no restart: Pult keeps its conversation, so a push it sends leads to Pult. Owner, 2026-11-20 («Ок»): this replaces the restarts of points 2-4 and 6: the script wakes Pult and the leads with a message through a one-shot session; Pult sends the push itself. Paid spend now about 0.02 USD.
- Keep-warm ping (owner, 2026-11-20, «так»; his idea): a lead that has working C sessions and has been silent for 50 minutes gets a ping message from the script (one-shot session, as above), so its cache (checked: leads write 1-hour cache) is warm when a C report comes. The lead answers with its standard status (owner: «Нехай пише стандартний статус»); an empty turn is not accepted by Claude Code (hub.md). Why it pays: a warm read is about 1/20 of a cold rewrite, so it wins while a report comes within about 16 hours. No ping when the lead has no working C.
- C fill check by the script (owner, 2026-11-20, «так»): `watch-servers.ps1` computes each live C's fill (the `last_usage` / `window_for` code of sessions.py, no model) every round and wakes its lead by message when a C passes 0.5, once per C. Cause it fixes: P ran fill only on an owner message or a C report (the catalogue C passed 0.5 at 14:58 UTC unseen).
- Before the build (owner, «так»): count the real watcher events per lead over the last 5 days (gone, finished, limited, stale, restart requested), to price the wake-by-message per event against today's idle wakes.

## Event count (2026-11-15..20, leads ClaudeDevKit, Zhratva, Prishch)
- 80 watcher exits other than exit 4; only 10 did real work: 3 `gone` (message plus a session command) and 7 `stale` (a push each). No `finished`, `limited` or `restart requested` exit. The other 70 were waste: 40 «already watching» (exit 6; a lead re-arming while its watcher still ran, median 138k units each), 12 «nothing to watch», 8 time-limit exits reported as exit 0 or -1 (add about 3.5M units to the idle total), 3 unreadable list, 7 kills and odd exits. All of these go away with point 6 (no lead watcher).
- C reports by SendMessage wake the leads far more often: ClaudeDevKit about 10 a day, Zhratva about 11 (peaks 22 and 27). So real watcher events are about 2 a day across all leads: wake by message per event is cheap, and the keep-warm ping matters more (it keeps those C-report wakes warm).

## Second design review (sonnet reviewer, 2026-11-20), for the builders
Earlier review: resolved by wake-by-message: Pult restart, heavy restart prompt, restart cost, messages lost while a lead is stopped (for events), latency. Still standing: marks written at detection (sessions.py:692-709, 764-783; `gone` grace in memory 817-830, 934), point 13 handoff issues, rewrite scope, thresholds, migration.
Critical:
- C1 permission mode: a SendMessage from another permission mode is held for the owner's approval (manager SKILL.md:246; project-lead SKILL.md:441, 578; resume-lib.ps1:105-110). Pult runs `auto` (start-servers.ps1:133); leads run `auto` or `bypassPermissions` (`Get-LeadPermissionMode`). The sender's mode must match its target.
- C2 the watch-servers loop is synchronous (529-641): run the sender with Start-Process, a 60 s wait and a kill, in a separate pass after the heal work.
- C3 delivery: keep a pending file (event id, target, text, tries); confirm by the event id appearing in the target's transcript; set LIMITS/STALE marks only after that; retry, then fall back to the phone push.
- C4 target down (Pult GIVEUP included): keep point 4 (one-shot PushNotification) as the fallback; one `Send-Wake -Target Pult|lead|phone` function.
Important:
- I1 pass the prompt by stdin or file, not argument (PowerShell 5.1 cuts at a double quote); restrict tools (`--tools`, check `claude --help`); a fixed template with an ASCII event id (event text comes from logs: injection risk); run from a temp cwd (home would load hub rules via hub-rules.py:45); target by id/ref, not name.
- I2 ping vs lead rules (SKILL.md:66-78, 603-605, 638-639): tag the ping so the lead answers with its standard status and nothing else; skip when the lead is busy; "working C" = live and busy; merge a due event into the ping; the ping may ask the lead to run fill for its C sessions and itself. About 29 visible statuses a day per lead with working C; the owner chose it.
- I3 C fill: persist «once per C» marks in a file (lost at WATCH-RESTART otherwise); reuse `sessions.py fill` (add `--over-only`); add the isSidechain skip.
- I4 700k push: as 0.7 of `window_for(model)`; scope (leads only?); through Pult's message or the one-shot push; persist once per session.
- I5 point 13: stop the old session before starting the new one (name clash; watch-servers.ps1:553); first prompt `/dev-kit:project-lead` plus the handoff; resend request to every C; a «handoff saved» marker file; no sends during a handoff; edit hub.md:149; `fill --self`.
- I6 one message per target per round, size cap, cooldown, one sender at a time.
- I7 a lead with no watcher shows idle: the version-bump restart (watch-servers.ps1:389) fires at once without the `ready` handshake; hub.md:152 («A script cannot send or receive SendMessage») becomes false.
Tests first: mode matrix (auto to bypass, bypass to auto); target mid-turn; target down (error, exit code); `-p` that needs approval (hang?); Ukrainian by stdin; cwd home vs temp; owner away 10 min (one-shot push and Pult's own push); lead with no watcher shows idle; ping answer on the phone; `sessions.py watch --id <x> --max-minutes 0` as a single round.
Smaller design proposed: drop the hook (point 5) and the 5-minute silence (point 3); drop watch-log.py and its tests; reuse watch-servers detection (HEAL-TASK/GIVEUP-TASK 170-233, Invoke-LimitCheck 237-261); one sender function; replace the `restart-leads.ps1 -Ask` file with a message; build in two phases (phase 2: point 13).
